# 设计取舍

## 渲染基础：Swing 窗口 + Java2D 软件渲染

纯 JVM：零原生库、零 Minecraft 类、零版本相关。窗口与事件用 AWT/Swing，绘制用 Java2D，字形由 `java.awt.Font` 提供（不必自带字形表）。

这是"一个 jar 覆盖所有游戏版本与三个加载器"能成立的前提：jar 里没有任何 Minecraft 引用，也就没有需要跟着游戏版本走的东西。代价是软件渲染——每帧走 CPU，适合编辑器式界面，不适合高帧率游戏内 HUD。

## 一个 jar，三份元数据，零个入口类

jar 内同时带 fabric.mod.json、META-INF/mods.toml、META-INF/neoforge.mods.toml，三份都**只有身份**（id、版本、依赖、图标），不声明 entrypoint、也没有 `@Mod` 类：它们唯一的作用是让 jar **进 classpath**。真正干活的是 `META-INF/kotlinmcui/entries` 里登记的一行——`<类名> client,standalone`：框架自己的发现先按环境列过滤、再加载类，与 loader 无关（专服因为不在环境列里，**连类都不会被加载**）。所以"支持另一个平台"只需要再加一份只有身份的元数据，不需要写入口类。

## 与无界面后端的分工

无界面后端（`kotlinmcuibackend`）负责 `install`（元数据与入口发现）；这一份用 `DslRuntime.start` 发布进程级工具 `WindowUtils`（实现了 `DslPlatformUtils` 的实例；`DslPlatform` 这一层已删除），并**自己构造根** `DslRoot(input, renderer, screenFactory, utils)`——绘制、输入、页面与每帧循环都在本仓，核心不再持有 provider。无界面后端发现 `kotlinmcuiwindow` 已安装时保持沉默。

启动顺序只有三条约束：

- `install` 必须在最前（重复调用会抛），元数据由 `install { WindowMetadata }` 提供。
- `start` 必须早于任何对进程级工具的读（`dslUtils` 等）；它返回 `false` 只说明进程槽已被别人发布，**不早退**。
- **根由本仓自己构造**（`DslRoot(...)`），构造之后再 `DslPreview.start(root)` 并开窗：运行时不再顺带起预览，漏了不会编译失败，只会"预览不启动"。

**没能成为进程级工具的所有者 ≠ 本后端不可用。** 进程槽归进程（第一个发布者），渲染归根：`start` 返回 false 时仍然构造自己的根并开窗；页面用**本根自己的 `WindowUtils` 实例**构建，而 `dslUtils` 仍是别的后端的。这样它能在 MC/web 已发布工具的进程里继续出窗口。

**发布出去的必须就是根用的那个实例。** standalone 在 `launch` 前先建 `WindowUtils` 并发布，入口随后复用它（`startWindow` 优先取 `dslUtils as? WindowUtils`），否则 `dslUtils` 会指向一个永远拿不到 `frame` 的副本，`capture`/`quit` 之类就会答非所问。
输入转发同理：**每个事件都要送到本窗口渲染的那个根**，不能去读任何全局根——共存进程里那会把光标与键盘派给别人的树，而且完全静默（一个对不上焦点的根本来就看起来像处理过了）。根由本仓自己构造，所以输入持有它、窗口持有它、页面持有它，**处处接参数**。

配对是**单向**的：这一份的元数据声明依赖无界面后端，反向则不是——无界面后端只在运行期用加载器的 mod 列表判断，不在元数据里引用这一份。这样无界面后端单独装也是完整可用的。

发布时机在**启动阶段**：入口只在 `DslRuntime.launch()` 里被调用（游戏里由无界面后端触发，standalone 由 `Standalone.main` 触发），而这个阶段内部要求进程级工具已发布，所以顺序恒为 `install` → `start` → `launch`。本仓没有 loader 入口类，因而也不存在"构造期发布"这个问题。

## AWT 的 headless 在入口对象初始化时清掉

游戏进程启动时 `java.awt.headless` 是 `true`，而 AWT 会在第一次被使用时把这个值**缓存**下来：之后再改属性也无效，`JFrame` 只会在事件线程上抛 `HeadlessException`，被 Swing 吞掉后表现为"窗口不出现且什么都不报"。

清掉它的地方是 `WindowEntry` 的**对象初始化**：框架发现入口时会实例化它，这远早于任何 AWT 使用；把属性改成 `false` 之后当场取一次默认工具包，把取值固定下来。条件是 `dslMetadata.environment == CLIENT`——专服上的注册文件不含 `server`，loader 在类加载前就把它滤掉，一次都不会碰 AWT；standalone 走 `STANDALONE`，本来就不是 headless，不需要清。

## 验收基线随入口模型更新过一次

验收截图拍的是框架的**入口页**，所以入口模型一改，图就会变——这不是渲染回归，而是页面内容变了。入口模型改造后，入口页在每条入口下显示它声明的端（`client` / `server` / `standalone`），旧的 `common` 徽标不再出现，因此旧基线图与新基线图不是同一张图。

由此得到两条用法：**哈希只在同一代核心内比较**（换核心后要重新钉基线，并写下为什么变），以及**比较之前先确认两条启动路径一致**——`gradlew run` 与 `java -jar` 的截图逐字节相同，才说明打包没有丢东西。
## 截图渲染内容，不是桌面抓屏

`capture` 把窗口自己的组件树渲染进一张内存图像，而不是抓取窗口占据的桌面区域。桌面抓屏要求窗口真的在最上面，操作系统的前台锁可能拒绝 `toFront()` 之后的状态，更重要的是会拍下那个矩形里的别的应用——一张悄悄属于别人的截图比没有截图更糟。

渲染内容也因此与前台状态无关：窗口被最小化（收起）期间同样能截到，实测结果与正常状态逐字节一致。这不是巧合，而是"渲染内容"这条路线本来就该有的性质——不要把"桌面抓屏需要窗口在前台"推广成"渲染内容也需要"。

## GUI scale 是连续值

窗口后端的 GUI scale 由窗口尺寸连续算出（`min(宽/320, 高/240)`，下限 1.0），不取整。理由与两个被否掉的备选见核心仓库的 ADR 0005：Java2D 的字形与描边都抗锯齿，取整就只剩代价。

页面自身的尺寸仍等于画布像素，`.scaled` 只作用于内容，所以改窗口大小不会溢出；布局随窗口尺寸连续变化。

## 物品图标

按 `assets/<命名空间>/textures/item/<名字>.png` 找，找不到再试 `textures/block/`。候选来源依次是版本客户端 jar（`versions/<版本>/<版本>.jar`）与 `mods/` 下的每个 jar，独立运行时退回 classpath；都没有就用一块平面替身加首字母，而不是画一个看起来不对的图标。

这一条是"不读 Minecraft 代码、只读 jar 里的 PNG"的边界：它读的只是资源文件，不涉及任何 Minecraft 类型。

## 图片按来源分派

`ImageHolder` 不再带 id：`source` 是 `ImageSource`，即 `Resource`（命名空间位置）/ `LocalFile`（本机文件）/ `Remote`（url）。渲染器与贴图缓存都 `when(source)` 按类型分派，缓存以 source 为键——一个资源位置永远不会被当成文件路径来读。

`localImage` 不在帧线程上读盘：第一次问一个文件只登记"加载中"并返回 `empty`，读盘与解码在自建的单线程守护线程上，完成后发布回会话线程（Swing 即 EDT）；下一帧命中条目直接拿到带尺寸的 holder。一个 `File` 条目同时存 `lastUsed`、holder 与已解码像素；`WindowTextures.get` 只上传已经解码好的像素，缓存里没有就返回 `null`，绝不 `ImageIO.read`。`remoteImage` 在本后端返回 `ImageHolder.empty`，因为这里没有 http 栈，下载也不该发生在帧线程。

条目在每帧入口做一次 sweep：超过 `TTL_MILLIS`（60 秒）没用过的条目连同像素一起淘汰，离开页面的图片不会一直占着内存。`reloadLocalImage` / `reloadRemoteImage` 丢弃对应条目：holder 与像素在同一个条目里，所以清一次就是两半都清，下一次 `localImage` 重新读文件。只有会话线程改缓存，后台线程只把结果交回 EDT，因此不需要并发容器。

## 图元输入已改成有类型的数组

四个图元重载现在把格式写进签名：纯色 quad 没有 image/uv，贴图 quad 两者都必需；三角形列表按顶点分别读 `x, y` 或 `x, y, u, v`，贴图形式固定四列，不随资源状态改成两列。三角形按 `colors.size` 推导顶点数，先检查 `N % 3 == 0` 与 `vertices.size` 的整除/余数关系，形状错误在查任何资源之前抛 `IllegalArgumentException`；空数组对两条三角形路径都是合法的空操作。任何一个非有限值、未测量值或转 `Float` 溢出的值都会跳过整次调用，包括最后一个顶点或 UV，因此不会留下半个三角形；目标矩形或图片标称尺寸非正则直接跳过。UV 的负值与越界是合法的贴图语义。

当前实现在查贴图前完成全部校验，资源分支按三态处理，判定只留在后端内部，没有公共加载状态、绘制返回值或回调：

- `source == null`、读取仍在进行、或本机文件尚未被 `localImage` 询问：本次**不画**，也不写任何命令；
- 标识形状无效（空、只有命名空间、以 `/` 结尾）、资源缺失、来源不支持（`Remote` 在本后端没有 http 栈）、读取确认失败：用后端唯一缓存的 16×16 品红/黑缺图纹理，按原几何、原 UV 与原顶点颜色绘制；
- 已解码：采样图片本身。

缺图纹理也是纹理，不会退化成纯色、无纹理或改变顶点步长。占位图与已解码图片使用同一条 UV 规则：holder 的名义宽高定义整张纹理的 UV 范围，实际像素宽高按 `textureWidth / nominalWidth`、`textureHeight / nominalHeight` 换算后铺满该范围。因此 2×2 的图片声明为 16×16 时，UV 0..16 显示整张图片而不是平铺八次；占位图尺寸与名义尺寸不同时，采样到的也仍是同一块图像。换算用双精度完成，极小但合法的名义尺寸（如 `Float.MIN_VALUE`）配合同样极小的 UV 仍会归一化为整张图片，不会先溢出成 Infinity/NaN 再画出空白。UV 的负值与越界不被钳制：整张纹理交给 `TexturePaint` 平铺，越界处重复采样。

四角或三顶点颜色先取平均作为整笔纹理的 tint。彩色 tint 逐 texel 乘到源贴图的 RGB 上（alpha 保持不变），再把整张贴图以 tint 的 alpha 做一次 `SRC_OVER`。这样 RGB 只作用于贴图本身，透明 texel 不会把 tint 刷到已有背景上，不透明度也只乘一次；白色 tint 不复制贴图，直接走 `TexturePaint` 快路径。渲染器只保留一份 tinted 副本，键为原图身份与 tint RGB，尺寸相符时复用，因此缓存有界，不是按 tint 无限增长的转换表。透视下的几何仍按角点投影（既有近似）：quad 把原始 UV 范围仿射映射到投影后的包围盒并被投影路径裁剪，贴图三角形把原始 UV 仿射映射到三个投影角点；两者都按调用给出的 UV 采样，不再用整张图替换，但逐像素透视校正仍留待后续，因此是“真实 UV 采样 + 仿射近似”。

延迟消费者若出现，必须在调用返回前拷贝可变的 `Rect`/UV 与两个类型化数组。

## 刻意不做

- 不在游戏窗口里画任何东西——正是这一点让它与游戏版本无关。
- 不引用任何 Minecraft 类。因此 `renderButton` / `renderSlot` / `renderContainer` / `renderTooltip` 是这一份后端的平面近似，用自有调色板，而不是读原版贴图。
- 不定位输入法候选窗口：Swing 没有这个 API，候选窗由输入法自己放置。
- 不做无障碍朗读（没有到读屏软件的桥），不播放按钮音效（唯一能发的是系统蜂鸣，比静音更糟）。

## 每帧循环由后端自己写

核心不再替后端驱动帧。每帧入口先做一次图片缓存 `sweep()`（见上一节），然后一帧就是三步，按这个顺序：

1. 把表面尺寸写给根与渲染器：`root.rect`（渲染 pass 会把它拷到每个已挂载的屏）与渲染器的 surface 尺寸（scale 由此派生）；
2. `context(renderer, renderParam, input.mouse) { root.component.render() }`——渲染器作为 context 实参传进去，不要让别的角色去"冒充"渲染器；
3. `renderer.flush()`。

顺序反了，屏会按上一帧的尺寸布局；第 2 步漏掉，窗口就是一片空白。 收窗口时**先 `root.close()`、再停驱动**：关掉根之后，晚到的一帧会在门口被拒，而不是画进一个正在消失的窗口。预览也不再由运行时顺带启动：`DslPreview.start(root)` 要显式调。

## 构建：兄弟仓优先，且不静默回落

本仓链接 `../kotlinmcui` 的核心产物：**只要兄弟仓存在就只用它**，缺主 jar 或缺 `-sources.jar` 都直接构建失败并指出该跑哪个任务（`jar` / `sourcesJar`）。曾经的写法是"本地缺失就回落到 jitpack"，而缓存里的发布版可能已是几个月前的核心——构建绿了，编的却是另一份库。
